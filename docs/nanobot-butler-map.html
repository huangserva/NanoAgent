nanobot -> 个人 AI 管家全景地图

目标不是把 nanobot 做成另一个 Hermes/OpenClaw 式重系统，而是守住一个极简 Agent runtime kernel， 让个人 AI 管家的记忆、任务、连接器、权限和产品体验通过 extension / external layer 演进。

Source: 当前代码结构 Kernel principle: core stays small, extend at edges Primary owner view: roadmap + boundaries
一句话判断

nanobot 已经具备 Agent runtime 的主干：message bus、AgentLoop、AgentRunner、tools、providers、 session persistence、channels、WebUI 和 optional memory bridge。

核心边界

进入 core 的只能是稳定运行协议、turn lifecycle、LLM/tool loop、session continuity、extension host 和安全边界。个人管家产品逻辑不能进入 agent/runner.py。

第一阶段验证

用一个 IM/WebUI、一个 provider、一个真实技能和一个提醒闭环，验证“可控、可测、可恢复”的个人工作助理场景。

必须进 core

  • 消息协议、队列和 turn lifecycle。
  • LLM/tool loop、tool/provider/hook contract。
  • session JSONL persistence 与可恢复性。
  • 通用安全边界：路径、网络、sandbox 原语。

不能进 core

  • 个人画像、复杂记忆策略、semantic/vector retrieval。
  • 任务 DAG、workflow orchestration、日历/邮件业务逻辑。
  • WebUI 页面状态、IM 富文本、settings 表单。
  • Hermes/OpenClaw 式统一上层自治系统。

图 2：Personal AI Butler 能力图

个人 AI 管家的目标能力可以很大，但每类能力都要明确归属。core 只提供运行时，产品能力通过外接服务、工具、技能、MCP 和 channel 扩展。

Conversation / IM Surface

当前已有channels/*, webui/*, channels/websocket.py
归属extension IM/WebUI 适配层
不要进 core平台富文本、消息卡片、媒体预览、settings 页面。

Reasoning / Tool Execution

当前已有agent/loop.py, agent/runner.py, agent/tools/*
归属core contracts + concrete tools
还缺更稳定的 tool audit、failure taxonomy、场景级回放。

Memory / Profile / Preference

当前已有agent/memory.py local Dream；memory_service/* optional SQLite + FTS5 bridge。
归属external；core 只接 bounded memory packet。
还缺配置入口、typed memory API、用户审阅/纠错/删除、memory eval。

Proactive Tasks / Follow-up

当前已有cron/service.py, heartbeat/service.py, agent/tools/cron.py, message.py
归属external task service 调用 nanobot。
还缺任务状态、重试、确认、失败恢复、任务审计。

Connectors / Actions

当前已有agent/tools/mcp.py, web.py, search.py, channel adapters, bridge/*
归属tools / MCP 或独立 connector service。
不要进 core每个 SaaS API、账号同步、业务对象模型。

Permission / Safety

当前已有pairing/*, channel allowFrom, security/network.py, tool path/sandbox checks。
归属safety primitives + policy UX
还缺按动作分级授权、确认、撤销、敏感工具审计。

当前已有能力

  • 完整 Agent loop 与 tool execution。
  • 多 provider、多 channel、WebUI 和 OpenAI-compatible API。
  • session persistence、local Dream memory、optional external memory bridge。
  • filesystem/shell/web/search/MCP/cron/message/subagent 等工具基础。

还缺的关键能力

  • 产品化 external memory：可配置、可审阅、可纠错、可删除。
  • 外部 task service：提醒、跟进、状态、失败恢复。
  • 权限和审计：动作级授权、敏感操作确认。
  • 场景级 eval：任务成功率、memory hit/miss、工具失败率。

图 3：演进路线图

每个阶段都要能独立验收。凡是会让 core 变重的能力，先做成外接服务、工具、MCP、skill 或 channel adapter。

Phase 0

守住 kernel 边界

冻结 core vs extension 原则，新增能力必须先选择 channel/tool/skill/MCP/service 路径。

  • 进入 core：contract、hook、safety、session reliability。
  • 外接：memory service、task service、WebUI surface、具体 connector。
验收

新增 butler 能力不改 agent/runner.py，尽量不改 agent/loop.py。

Phase 1

真实最小场景验证

用一个 IM/WebUI、一个 provider、一个技能和一个提醒闭环验证个人工作助理。

  • 当前可用：channels/websocket.py, providers/*, tools/filesystem.py, tools/cron.py, tools/message.py。
  • 缺口：权限确认、memory 默认启用策略、场景测试。
验收

稳定对话、可靠工具调用、可接受延迟、session continuity 清楚、失败可恢复。

Phase 2

Memory productization

把 memory_service/* 从可注入桥推进到可配置、可审计、默认关闭的产品能力。

  • 进入 core：optional bridge hook 和 bounded memory packet。
  • 外接增强：typed memory API、审阅/纠错/删除、memory eval。
验收

跨 session recall 可测，误召回可发现，关闭 memory 后 core 行为不变。

Phase 3

Task / proactive butler layer

建立外部 task service，管理提醒、跟进、重试、确认、审计，不让 workflow 进入 AgentLoop。

  • 当前基础：cron/service.py, heartbeat/service.py, tools/cron.py, tools/message.py。
  • 不进 core：任务 DAG、调度策略、业务规则。
验收

2-3 个长期任务稳定运行，例如提醒、每日简报、等待用户回复后的跟进。

Phase 4

Connector and action ecosystem

通过 MCP/tools 接应用，避免 nanobot 变成集成巨石。

  • 进入 core：tool contract、sandbox/security、audit hook。
  • 外接：calendar/email/todo/files/browser 等 connectors。
验收

新增 connector 不改 agent/loop.py / agent/runner.py。

Phase 5

Evaluation / observability

让 personal butler 可测、可回滚、可迭代。

  • 当前基础：pytest、hooks、progress events、logs。
  • 外接增强：scenario replay、memory hit/miss、任务成功率、工具失败分类、latency budget。
验收

每个真实场景可自动回放，失败能定位到 provider/tool/memory/channel/task 层。

第一阶段最值得验证的真实使用场景

个人工作助理闭环

用户在一个 IM 或 WebUI 中要求 nanobot 读取/总结本地工作材料，明确表达一个偏好， 设置一个提醒；到时间后，nanobot 主动发回简短结果，并在下一轮能引用该偏好。

要覆盖的当前模块

  • channels/websocket.py 或一个稳定 IM channel。
  • providers/* 的一个实际 provider。
  • agent/tools/filesystem.py, cron.py, message.py。
  • session/manager.py 和 optional memory_service/bridge.py。

验收指标

  • 用户不需要理解内部模块也能完成任务。
  • 工具调用和提醒投递稳定，有明确失败反馈。
  • 偏好 recall 可解释、可关闭、可纠错。
  • 新增场景不要求改 agent/runner.py。

维护说明

这个文件是单文件静态 HTML，可直接在浏览器打开。后续维护时只追加或调整已有分区，不需要构建步骤。

更新时先检查

  • 新增能力是否真的属于 core。
  • 是否能通过 channels/, tools/, skills, MCP 或 external service 实现。
  • 是否新增了 agent/loop.py 或 agent/runner.py 的产品分支。
  • 是否有对应场景验收和回归测试。

优先拆重的位置

  • channels/websocket.py：WebUI HTTP surface 可拆 sessions/settings/media/transcript。
  • agent/memory.py：local store、Consolidator、Dream service 可分边界。
  • cli/commands.py：gateway runtime 组装逻辑避免继续膨胀。
  • agent/loop.py：新产品逻辑优先迁到 hook/service/tool。
